# Operating DEEP V2

DEEP V2 is the project's first release with a hardened reference implementation.
Automated verification and defensive defaults do not constitute an independent
security audit. Keep keys, configuration, and adapter programs under your control.

## Access and credentials

`deep init` creates a private server and an authorized client. `init --public`
explicitly permits clients without a client certificate. Server authentication,
pin verification, TLS 1.3, hybrid X25519MLKEM768 key establishment, and ML-DSA-65
signatures remain mandatory in both modes.

A private server's `allowed_client_pins` is its authorization list (maximum 256).
A matching pin authorizes all resources served by that node; V2 does not define
per-path permissions. Remove a pin and restart the server to revoke it and close
existing sessions. There is no automatic certificate-revocation service.

Use one client identity per person or device, generated on that device with
`client-init`. Back up keys through a trusted private channel. Do not distribute
the initial client's key to multiple people. `inspect --certificate` prints only
public information: pin, authority, algorithms, validity interval, and usage.
Certificates generated by the CLI expire after one year. Generate replacement
identities in new directories before expiry and distribute verified new pins.

To rotate a server key, prepare a new node directory, copy only intended content,
update client pins through a trusted channel, and switch to the new server.
Clients accept one configured server pin per endpoint, so coordinate that change.
For client rotation, temporarily authorize both public pins, switch the client,
then remove its old pin and restart the server. Protect archived private keys.

## Local file protection

The initializer creates a new directory and never overwrites an existing one.
On Unix it uses directory mode 0700 and private-key mode 0600. On Windows it
removes inherited access from the new empty directory and grants the current
user full access, inherited by its files. If Windows ACL setup fails, initialization
fails before writing any keys. Administrators and backup software remain part of
the machine's trust boundary. Moving files elsewhere can change their permissions.

The resource root must be separate from the server configuration and certificate
and key paths. Startup resolves symlinks and rejects those files beneath the
served root. Keep all other secrets and backups outside the root as well. The
server account needs read access to content and its own credentials; use a
separate unprivileged account for an exposed service. Generated configurations
listen only on the explicit address you supplied (loopback by default).

## Server configuration

Required fields are `version` (2), `authority`, `listen`, `root`, `certificate`,
`private_key`, and `access_mode` (`private` or `public`). Private mode additionally
requires a nonempty `allowed_client_pins`; public mode must omit it or use an empty
array. Field names are case-sensitive. Unknown keys, duplicates, null values,
and extra JSON documents are rejected. Paths are relative to the configuration.

Optional numerical limits use the default when omitted or set to zero:

| Field | CLI default | Maximum |
| --- | ---: | ---: |
| `handshake_timeout_seconds` | 5 | 60 |
| `idle_timeout_seconds` | 30 | 600 |
| `transfer_timeout_seconds` | 30 | 3600 |
| `session_timeout_seconds` | 3600 | 86400 |
| `max_connections` | 128 | 4096 |
| `max_connections_per_peer` | min(16, global limit) | Global connection limit |
| `max_requests_per_session` | 1000 | 1000000 |
| `max_bytes` | 1073741824 (1 GiB) | 1099511627776 (1 TiB) |
| `requests_per_minute` | 120 | 1000000 |

Per-peer accounting groups TCP clients by source IP; clients behind the same NAT
share limits. Connection and request controls are resource limits, not protection
against a large distributed denial-of-service attack. The operating environment
must provide any required firewall, traffic filtering, monitoring, and service
supervision. The library also permits at most 240 accepted connections per peer per fixed minute and tracks at most 4,096 recent peer budgets. Inactive expired budgets are reclaimed; a full table rejects new peers.

Restart to apply configuration or identity changes. Ctrl+C closes the listener
and active sessions. A custom library resource handler must honor cancellation
and unblock reads when its body is closed. Network limits cannot stop a custom
handler that ignores this contract.

## Safe client use

`fetch` deliberately writes raw resource bytes to standard output. For untrusted
or binary content, use `--output new-file` and inspect it with an appropriate tool.
Downloads to files are verified before publication, never overwrite an existing
file, and require a filesystem supporting hard links (such as NTFS or ext4).
A failed raw stdout transfer may already have printed partial bytes; discard them.
The `open-uri` viewer buffers at most 1 MiB, verifies completion and integrity,
and escapes terminal controls and directional-formatting controls before display.

Treat adapter configuration as trusted local code/configuration. An executable
adapter runs a configured local program with your account's privileges. Never
install a resolver or accept a server pin solely because an untrusted page asks
you to. There is no public DNS ownership or certificate authority implied by a
custom `.alpha`, `.hell`, or other DEEP network name.

## Build and release artifacts

Use a patched Go 1.27.1 or newer toolchain. `scripts/build.ps1` builds the local
Windows executable. To create local release archives for six OS/architecture
combinations, run:

```powershell
python scripts/release.py
```

The output directory must be new. To build only one target:

```powershell
python scripts/release.py --targets windows/amd64 --output dist/windows-test
```

The script creates six binary archives, a source archive, `BUILD-MANIFEST.json`, and `SHA256SUMS`.
It never uploads, publishes, tags, or signs a release. SHA-256 checksums detect
changes only when obtained from a trusted source; they are not publisher
signatures. Archive timestamps and ownership are normalized. Reproducing identical
archives requires identical source files, Go toolchain, and Python/zlib versions.
Cross-compilation alone does not prove that each artifact works on its target OS.
CI checks build/test behavior on Windows, Linux, and macOS; the validation report
states what was actually run locally.
